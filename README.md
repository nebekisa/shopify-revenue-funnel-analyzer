# Shopify Revenue & Funnel Leakage Analyzer

A production-style analytics engineering project that models how a real
DTC e-commerce team would diagnose revenue leakage across the purchase
funnel — from messy event data to a founder-facing executive dashboard.

## Business problem

Traffic is up. Revenue is not. The founder wants to know:
**where are we losing customers, how much revenue is on the table,
and what should we investigate first?**

## Architecture

    synthetic events  →  raw parquet  →  DuckDB staging views  →  fct_sessions
                                                                      ↓
                                                   funnel / revenue / segment SQL
                                                                      ↓
                                                       Streamlit dashboard

- **Python** generates behaviorally realistic event data (not random rows).
- **DuckDB** holds staging views and the session-grain fact table.
- **SQL** owns all metric logic so it is portable and testable.
- **Streamlit + Plotly** surface the metrics for a non-technical founder.

## Data model

| Table | Grain | Purpose |
|---|---|---|
| `traffic_logs` | event | Session entry + product views |
| `cart_actions` | event | add/remove cart |
| `checkout_events` | event | checkout_started / payment_attempted / payment_failed |
| `orders` | order line | paid / cancelled / refunded |
| `fct_sessions` | session | the core analytical model |

### Why a separate `checkout_events` table?

You cannot infer checkout initiation from orders — orders only fire on
success. Without a separate checkout event stream, checkout abandonment
is invisible and the funnel silently collapses two distinct stages into
one. Real Shopify/webhook pipelines separate these, and so does this
project.

## Data-generation methodology

Each session is generated by walking a **state machine**:
view → (maybe) add to cart → (maybe) checkout → (maybe) payment → (maybe) purchase.
Segment-level multipliers for device and traffic source modulate the
transition probabilities, so heterogeneity emerges naturally rather
than being forced.

Funnel ranges targeted:

| Stage | Expected range |
|---|---|
| Add-to-cart / view | 10–25% |
| Checkout / ATC | ~40–60% |
| Purchase / checkout | ~50–70% |
| Overall session conversion | 1.5–3.5% |

The generator prints a validation report after each run.

## Intentionally introduced data-quality issues

| Issue | Rate | Rationale |
|---|---|---|
| Missing `traffic_source` | ~3.8% | Ad-blockers / consent |
| Duplicate traffic events | ~1.2% | Tracking double-fire |
| Duplicate cart events | ~1.8% | Retry storms |
| Invalid order status | ~0.4% | Partial writes / typos |
| Orders without checkout | ~2.1% | Attribution gaps |

These are **reported**, not silently dropped. Staging SQL handles them
defensively (e.g. `COALESCE(traffic_source, 'Unknown')`).

## Funnel definitions

- **Add-to-cart rate** = `add_to_cart_sessions / product_view_sessions`
- **Checkout rate** = `checkout_sessions / add_to_cart_sessions`
- **Purchase rate** = `purchase_sessions / checkout_sessions`
- **Overall conversion** = `purchase_sessions / product_view_sessions`

All rates are computed on **distinct sessions**, not raw event counts.
Raw-event rates get inflated by duplicate tracking, repeated product
views, and multi-item carts.

## Revenue methodology

- **AOV** = `gross_revenue of paid orders / number of paid order lines`
- **Net revenue** = `gross_revenue − discount_applied`
- **Estimated Revenue Opportunity** =
  `abandoned_checkout_sessions × AOV`

This is an **estimate**. Abandoned sessions do not necessarily have the
same expected order value as successful ones.

## Assumptions and limitations

- Synthetic data. Not real Shopify data.
- Abandoned-revenue figure is a scenario estimate, not recovered money.
- AOV-based leakage assumes abandoned sessions resemble converted ones.
- Attribution is first-touch within a session, simplified.
- Checkout events are simulated.
- Funnel correlations do **not** imply causality.
- The 5% improvement figure is a **relative** scenario, not a forecast.

## Example business findings (from a default run)

- Overall session conversion ≈ **2.4–2.8%**.
- The largest single drop-off is **checkout → purchase**.
- **Mobile** checkout conversion is materially lower than **desktop**.
- **Meta** traffic converts lower than **Direct**.
- Estimated abandoned-checkout revenue is non-trivial and worth
  investigating before increasing ad spend.

## Important Analytical Limitations

**Read this before quoting any number.**

1. The dataset is synthetic. Numbers are internally consistent, but
   they are not evidence about any real business.
2. "Estimated Revenue Opportunity" is a **scenario**, not a forecast.
3. The AOV used for leakage assumes abandonment resembles conversion.
   It usually does not, exactly.
4. Attribution is first-touch and simplified.
5. Checkout events are simulated by a state machine; real checkout
   webhooks carry more signal and more noise.
6. Funnel correlations do not establish causality. A low mobile
   conversion rate could be device, price, creative, audience, or a
   measurement artifact.
7. The 5% figure is a **relative** improvement, not five percentage
   points. Improving checkout conversion by 5% relative means
   `current_rate × 1.05`.
